# Movie Library Recovery

用于电影库整理、去重、归类或改名之后的安全回滚。目标是恢复整理前的结构与文件，不是继续“修正”当前结构。适用于按大洲/国家/导演/影片组织的媒体库，尤其是 SMB 网络卷。

## 0. 进入回滚模式

当用户表示整理有问题、要求“完全恢复原样”或不再信任当前结构时：

1. 立即停止继续整理、去重、改名和清理。
2. 明确回滚范围（例如只恢复亚洲，其他大洲保持现状）。
3. 确认原始快照、当前根目录、回滚暂存区、回收站和待归类区的实际路径。
4. 回滚期间所有动作默认是**可逆移动**，不做 `rm`，不清空任何 staging/trash。
5. 只有完成逐国验证并由用户确认后，才讨论清理暂存区或回收站。

## 1. 建立并冻结基准

原始快照至少应保存：

- 每个文件和目录的相对路径
- 文件/目录类型
- 文件大小（可行时保存 mtime）
- 对重要视频可保存 md5 或前 32 MB 指纹

任何旧 diff、旧索引、旧计划都可能因前一批移动而失效。每批移动后必须重新读取实际状态，不能继续盲用旧索引。

建议将恢复目标定义为：

```text
target = snapshot files that are absent from their original path
source pools = current extras + rollback staging + area trash + explicitly approved quarantine
```

快照中的“缺失”不等于数据丢失：它可能已经在新导演目录、回收站、待归类区，或者只是 SMB 的不可访问幽灵条目。

## 2. SMB 扫描与批处理

不要对大型 SMB 卷一次性执行 `os.walk`、全树 `find` 或逐个 `exists` 探测。采用以下节奏：

1. 按国家或大区扫描。
2. 国家较大时再按导演或目录批次扫描。
3. 使用 `os.scandir()` 获得实际可见项，避免依赖陈旧清单。
4. 只读生成计划，计划源文件必须一对一。
5. 每批移动约 40–100 个文件，或一组经过集合验证的完整影片目录。
6. 批次结束立即检查：目标已出现、源已消失、失败数为 0，再开始下一批。

### 全库比对：一次遍历 + 内存集合差（2026-08-23 验证）

对"快照 vs 现状"这类**全库差异核对**，逐条 `os.path.exists()` 探测几千个路径会拖垮 SMB 卷——实测每秒只能完成个位数探测，300 秒超时后一无所获。正确做法是把"多次网络往返"变成"一次遍历 + 内存比对"：

```python
# 1) 每棵树只 os.walk 一遍（含 staging/trash/待归类），收集 NFC 归一的完整文件集合
def nfc(s): return unicodedata.normalize('NFC', s)
files = set()
for dp, dn, fn in os.walk(root, onerror=lambda e: errors.append(str(e))):
    for f in fn:
        files.add(nfc(os.path.join(dp, f)))
# 2) 快照缺失判定全部在内存完成：nfc(join(BASE, rel)) not in BF
# 3) 候选来源查找用 endswith('/' + basename)，同样纯内存
```

实测：~4700 文件的暂存区遍历 246s、6500 文件的主库遍历 286s，但之后 503 条快照的逐条判定 + 候选分类在内存中瞬间完成，全程一次跑完无超时。

配套工程要求：

- **分阶段落盘**：每扫完一棵树就把结果 `json.dump` 到 `/tmp`，中途被杀不丢已完成部分。
- **onerror 回调存字符串**：`os.walk(onerror=...)` 收到的是异常对象，直接 append 进列表会让 `json.dump` 抛 `TypeError: Object of type FileNotFoundError is not JSON serializable`——必须 `str(name)`。
- **前台运行**：Hermes 后台进程的 stdout 重定向可能静默丢日志且难以跟踪；这种长扫描用前台 + 高 timeout 更可靠。
- **NFD 容错进比对逻辑**：缺失判定前先查原始路径再查 NFC 变体，避免把 NFC/NFD 差异误报为丢失。

执行移动优先用 Python `os.rename()`：

```python
os.makedirs(os.path.dirname(dst), exist_ok=True)
os.rename(src, dst)
```

执行前再次检查 `src` 存在且 `dst` 不存在。遇到异常只记录并停止该批，不用替代路径猜测。

## 3. 可靠的归属匹配

匹配证据按强度排序：

1. 原始相对路径直接对应（例如回收站保留原国家/导演/影片子树）。
2. `文件名 + 影片目录名 + 影片目录内相对路径` 完全一致。
3. 导演目录名称发生格式变化时，允许只对导演名做 NFC、去空格、去点号后的规范化比较。
4. 在合集和导演目录之间移动时，允许放宽导演目录，但仍必须保持影片目录名、相对路径一致，并确认源唯一。
5. 只有对真正独特的 release 文件名或 UUID，才可使用全局唯一 basename；普通元数据绝不允许这样做。

影片根目录应取“包含视频的最深非结构目录”。以下目录是结构目录，不是影片根：

```text
BDMV STREAM BACKUP CLIPINF PLAYLIST CERTIFICATE
Sample Proof Subs CD1 CD2 VIDEO_TS AUDIO_TS
```

计划必须检查：

- 一个源不能对应两个目标
- 两个源不能竞争一个目标
- 当前已经位于任何快照目标路径的文件不能当作待迁移源
- 目标父目录可创建，但不能覆盖现有文件

### 通用文件名黑名单

以下名称不能仅凭 basename 跨影片恢复：

```text
movie.nfo
poster.jpg
fanart.jpg
landscape.jpg
backdrop.jpg
logo.png
folder.jpg
clearlogo.png
```

这类文件必须通过影片目录上下文匹配；找不到上下文就列为人工复核。否则很容易把一个影片的 `movie.nfo` 误放到另一个影片。

### 回收站改名文件

回收站中的文件可能被改成 `*-重复`、`uuid-file-*` 或简化名称。只有在下列证据至少两项吻合时才建立显式映射：

- 原始目录/影片上下文
- UUID 前缀或原始 basename 片段
- 文件类型和扩展名
- 文件大小、md5 或前 32 MB 指纹
- 用户已经确认的历史裁决

映射写入计划后再执行，不能在脚本中临时凭直觉改名。

## 4. 整目录恢复的安全条件

整目录移动可以显著减少 SMB 操作，但只在以下条件全部满足时使用：

- 源目录文件集合与快照目标目录文件集合完全相等
- 目标目录不存在
- 源目录计划之间没有父子嵌套
- 移动不会携带未在快照中确认的额外内容
- 目录内没有需要单独处理的歧义文件

如果多个计划互相嵌套，只保留最上层且已完成集合验证的计划；否则父目录移动后，子计划会变成假失败或重复操作。

## 5. NFD / SMB 幽灵条目

如果 `scandir` 可以列出一个 NFD 分解 Unicode 名称，但对该条目执行 `stat`、`isdir`、`join` 或 `rename` 返回 `ENOENT`，将其标记为不可访问幽灵条目：

- 不要反复重试
- 不要删除
- 不要把它当成已恢复
- 记录原始路径、Unicode 形式和错误
- 最终报告单列“不可访问幽灵”

若需要规避缓存，可用 NFC 名称新建替代目录，但必须明确它只是替代路径，不能冒充原条目已经恢复。

### 未匹配条目的归因报告（2026-08-23 模式）

用户问"没对上的是什么原因、还能对上吗"时，不要只报缺失数字，要给**可行动的归因分类**。对每条缺失项按"原因 × 能否恢复"两个维度分桶：

1. **计划已生成未执行**——recovery 计划文件已存在且源仍在，直接执行即可。
2. **从未进入精细匹配流程**——只跑过粗批量的区，需补生成计划（预期绝大多数有候选）。
3. **通用元数据名被主动排除**——黑名单文件因防误配被禁用 basename 匹配，需升级为"影片目录上下文匹配"后可恢复，这是安全设计而非数据丢失。
4. **真无处可寻**——staging/trash/待归类/库内他处全部没有候选，列清单交用户定夺。

每桶给数量 + 样本 + 恢复路径。这样回答把"还能对上吗"变成量化结论（如：503 缺失 = 281 可立即执行 + ~118 补计划 + ~70 升级规则后可恢复 + ~34 真丢失），避免用户误以为所有未匹配项都是永久损失。

### 缺失 ≠ 删除：宣布"真丢失"前必须做指纹级复核（2026-08-23 实测）

basename 候选匹配找不到 ≠ 文件没了。实测案例：审计报 34 条"无处可寻"，用户质疑"我从没让 Agent 做过删除动作"，逐条做内容指纹复核后**只剩 ~3 条真疑点（误报率约 90%）**。原因和复核方法：

- **父目录被改名/重排后 basename 死板匹配失效**：如《蛇草莓》实际躺在 `西川美和.Nishikawa Miwa/西川美和 蛇草莓/` 下，按原路径 `合集/西川美和 蛇草莓/` 匹配自然失败。→ 用**片名指纹**（中文片名、日文原名、英文 release token、罗马字变体）在全部四个位置全库搜。
- **Unicode 变体导致同物不同名**：`Gubijinsô` vs `Gubijinsô`（ô 的组合字符差异）、日文全角片假名。→ 指纹取词时要避开易变字符，或同时搜 NFC/NFD 两形式。
- **`._` AppleDouble 条目冒充真身**：115/SMB 会为每个条目生成 `._文件名` 元数据伴生件，`ls -la` 和 os.walk 都能看到它们。判断"目录里还有没有东西"时必须过滤 `basename.startswith('._')`，否则会把元数据残骸当成影片还在的证据，也会把真身已丢误判为还在。
- **多版本互替**：KOOK 版 vs WiKi 版同名影片，正片在但版本路径与快照不同——这属于版本决策问题，不是丢失。
- **云盘同步临时件**：无扩展名 UUID 文件是同步产物，本来就是垃圾。

只有指纹搜索四个位置全空 + 用户确认没有其他副本来源，才允许写"真丢失"。

### 115 等虚拟挂载卷的双视图失真（2026-08-23 定性，机制已实锤修正）

用户最终发现：消失的滨口龙介影片在 CD2 里能播放、网盘 App/网页/官方回收站却全找不到——**不是**"App 改动不即时反映"那么简单。真实链路是 Mac ←SMB← NAS(192.168.10.33) 上的 CloudDrive2 容器（FUSE `/media/CloudDrive`）←115。事故根因：CD2 向 115 发改名请求时文件名字段变空被拒（容器日志 N×「rename uploadfile failed」），文件在 115 的目录索引里空名隐身；本体和文件 ID 完好，所以 CD2 按 ID 换直链仍能播放。

操作纪律：
- 遇到"挂载点没有但某处能播/能看"，先查 CD2 缓存库有没有该文件的 ID+大小记录——有记录=服务器端活着，走隐身救援流程，不要先怀疑数据损坏。
- 大批量移动优先在 App/网页端做，或经挂载点小批挪动后**双向刷新验证**（App 里看一眼 + 挂载点 rescandir）。
- 出现"两边不一致"时任何一侧都不要先删除；向用户解释用"目录索引隐身/三层各见各的真相"框架。
- **完整取证与救援手册见 `references/clouddrive2-rescue-playbook.md`**（缓存库 JOIN 查询、路径前缀陷阱、Web UI 移云下载法、字节核对标准）。

## 6. 验证与汇报

逐国验证，而不是只看移动命令返回成功：

1. 快照文件在原路径存在数。
2. 仍缺失数，并按视频、字幕、nfo、图片、样片、UUID 分类。
3. 仍位于 staging/trash 的源数。
4. 额外文件和额外目录数。
5. 失败/歧义/不可访问条目清单。
6. 对关键视频做大小或 md5/前 32 MB 复核。
7. 复查顶层国家→导演→影片层级，防止跨国家或跨层嵌套。

只有在所有国家完成复核、回收站和暂存区仍保留、已知缺口已明确列出后，才能说“回滚执行完成”。如果仍有缺口，应准确说“部分恢复完成”，不能用移动批次成功代替最终验证。

## 7. 回滚收尾阶段（2026-08-23 实战流程）

回滚主体完成后，通常还有四类尾巴要处理，按序执行：

### NFO/元数据恢复
- 通用名 `movie.nfo` 只按**所在电影文件夹名**配对（用户拍板的硬规则，防止跨片误配）；视频同名 nfo 才按文件名匹配。
- 恢复 nfo 前先检查目标目录有没有正片：**只放 nfo 进无视频夹会制造孤儿元数据**——若正片还在暂存区，应把正片一起配对回来；若正片是当年去重时故意丢弃的，则不该建空壳夹。
- 大量 nfo 缺失的常见去向：暂存区换父目录、回收站被改名（`小城之春-重复-nfo` 这类）、CD2 隔离区。逐层找。

### 与历史去重决策交叉核对
把恢复清单和当年的 drop 决策记录（含保留路径+理由）比对：恢复项撞上 drop 项时逐条分类——sample 垃圾/低版本/纯字幕包 = 无害；EXACT 正片回来 = 真重复，交用户裁决留哪份。**不要默认按原决策反悔**：用户可能改主意（实例：《老笠》两份都保留，因为一份海报字幕配套更全）。
重复判定首选 **CD2 缓存库 `files.file_hash` 字段**（存 115 服务器端 SHA1，JSON 形如 `{"Sha1":"61A7..."}`）：同路径两份文件 SHA1 一致 = 字节级同一文件，比下载比对 md5 前 32MB 更强且零流量（实例：《离开的女人》16.4GB 双份凭 SHA1 实锤）。

### 暂存区退役
- 先收割真实文件（排除 `._`/`.DS_Store`），再对剩余物整体 `mv` 进回收站改名归档——不要试图逐个清理几千个 AppleDouble 垃圾和不可读幽灵条目。
- 收割时做电影级冲突检测（不是文件名级）：同名 `fanart.jpg` 在不同影片夹里不冲突，但整部电影双份才是真问题。

### 回收站清理前的唯一副本审计
用户问"这个回收站能删了吗"时，**必须先审计唯一副本再回答**：
- 对照当年去重决策验证每批有存活副本；
- 定点检查可疑单件（如回收站根目录的孤立 mkv 可能是某片唯一可播版本——实例：《下女》1960 MiniSD 是唯一可访问副本，另一个版本是索引损坏的幽灵件）;
- 用**当前状态**核实，不能用早间扫描快照下"主库没有"的结论——当天自己搬过几百个文件后快照就过期了，要用定点 `ls` 复核。
- 审计通过后可删：首选用户在 115 App/网页端删（服务器原生秒级）；SSH `rm -rf` 经 FUSE 实测也可行——数千文件后台数分钟跑完（background+notify_on_complete 模式），删除前唯一副本审计不可省，完成后必须定点核验（夹消失+关键文件完好）。

## Pitfalls

- 把 CD2 缓存库当现状用：`dir_cache.sqlite` 是**时点快照**——查服务器端文件 ID、file_hash（115 SHA1）、历史路径它是权威，但当天执行过任何移动后它就不再反映挂载层现状；判"现在有什么"必须定点 `ls` 复核。
- 在 FUSE 挂载上跑全树 `find`：连 `find | wc -l` 都会 240s 超时（云端 API 逐条往返）；统计类需求改查本地拷贝的缓存库，或分目录定点 ls。批量删除/移动类长任务用 background+notify_on_complete 跑。
- 恢复 nfo 时不检查目标目录正片状态：孤儿元数据夹比缺 nfo 更糟；nfo 与正片必须配对闭环。
- 恢复文件与历史去重决策冲突时不核对：可能把当年故意丢弃的重复件搬回来制造真重复；也可能反过来误删用户想保留的副本（去重决策可被用户推翻，但要明说）。
- 用过期扫描快照判断"主库没有 X"：当天自己执行过批量移动后，快照即失效，必须定点 `ls` 复核后再下结论。
- 回收站清理只按批次记录审计：回收站根目录的孤立单件（改名副本、救回件）不在任何批次清单里，恰恰最可能是唯一副本。
- 使用旧 diff 继续移动：前一批改变了源路径，后续计划会指向不存在或已被占用的路径。
- 对 SMB 卷逐条 `exists()` 探测做全库核对：几千次网络往返必然超时且拿不到任何结果；必须一次遍历收集集合后纯内存比对（见 §2）。
- `os.walk(onerror=...)` 的回调直接 append 异常对象：后续 JSON 落盘会抛 `TypeError: ... not JSON serializable`；要 `str(name)`。
- 只按 basename 匹配：`movie.nfo`、海报和 `landscape.jpg` 会跨影片串位。
- 把 `scandir` 能看到的 NFD 条目当作可操作文件：SMB 可能只返回缓存残影。
- 把回收站中的“重复”文件永远视为垃圾：用户要求回滚时，它们可能正是需要恢复的原件。
- 宣布"真丢失"前只做过 basename 候选匹配：目录改名/Unicode 变体/多版本互替都会造成误报，必须先做内容指纹级复核（片名中/日/英 token 全库搜四个位置）。
- 把 `._` AppleDouble 伴生文件当成影片本体：判断"目录里还有什么"时必须过滤 `._` 前缀条目。
- 盲信快照基准：快照抓自可能失真的虚拟挂载视图（115 等），落盘后要抽查已知目录做合理性校验；发现知名导演整目录为空这类可疑空洞要当场向用户提出。
- 在虚拟挂载卷上做大批量移动后只验证单侧：挂载视图和网盘 App 视图会分叉，移动操作可能被降级为"根目录重新上传"；每批之后双向刷新验证。
- 一个脚本扫描和移动整个 SMB 大卷：超时后无法判断哪些动作已经执行，必须改为小批次并逐批核对。
- 整目录计划存在父子嵌套：父目录成功后子计划必然显示源缺失，造成误报。
- 验证只统计视频：用户要的是原样恢复，nfo、字幕、图片和 UUID 也要分类报告；但不能用通用文件名跨影片猜测归属。
