# Course Series Translation — 课程系列风格匹配翻译

用于在已有中文翻译的课程系列中，翻译后续课时并保持全系列风格一致。

## 适用场景

- 用户要求翻译课程第 N 课（如"翻译博弈论第 9 课"）
- 该系列已有之前课时的中文译文（L1–L8 等）
- 译文是"演讲稿风格"而非学术风格
- 用户强调整体性和风格统一性

## 反模式

- ❌ 不看已有译文直接翻译——风格必然偏离
- ❌ 忽略 frontmatter 格式——全系列不一致
- ❌ **用户问「你是不是概括的有点多？」不等同于「给我重做一版更详细的」**——先回答：解释你的翻译策略，然后问用户是否需要修改。直接开干重写大概率白做，用户反而会回来选上一版。
- ❌ **遵循已通过的版本作为风格锚点，而非最新的重写**——如果用户说「之前的版本我是满意的」，这个版本就是当前系列的风格基准。任何后续改动（L10+）必须以这个版本为锚点，而不是你最新写的扩展版。
- ❌ 保留原文噪音标记（>>, [snorts], [laughter] 等）——译文应是干净流利的文本
- ❌ **把「保留作者口气」等同于「增加细节」**——这是最常见的翻译策略陷阱。用户说「感受不到作者口气了」不一定是要你停止压缩、逐句翻译。可能你的压缩幅度是对的，但作者的叙事节奏和个性化表达在压缩中被磨平了。优先保留：主讲人的独特语气、论证递进感、修辞节奏。数据细节和枝节案例可以合理压缩，但故事的骨架和讲述者的「人味」必须保留。
- ❌ **用户说「更详细」就全盘加细节**——先搞清楚缺的是「数据/内容」还是「风格/叙事结构」。大多数时候用户要的是后者。过度加细节反而破坏阅读节奏，用户会倒回来选上一版。先读已有译文的篇幅和风格密度作为参照锚点，不要偏离太远。
- ⚠️ **区分「质疑概括程度」和「要求最大限度展开」**——这是两个完全不同的信号。如果用户说"你是不是概括的有点多？"这是质疑你的策略，回答后问是否需要改，不要直接开干重写。但如果用户说"如果能详细，就尽可能的再详细一点"——这是明确授权你超出正常密度、做最大限度的展开。此时应从三个维度同时扩展：(1) 补回之前压缩掉的论证细节和枝节案例；(2) 给每个关键论点补充具体的国家名、人名、百分比、年份等数据锚点；(3) 展开叙事节奏——增加语气递进、转折句、和原文引语的完整译文。不要在"该不该详细"上犹豫，这是绿灯信号。
- ❌ **第三人称转述风格**——不要把课程翻译成"讲者指出/讲者做了/讲者用了一个例子来说明"这样的书评式语言。源文件是讲课，译文也必须是讲课。读者要感受到讲师在直接对他们说话，而不是有人在描述讲师做了什么。见「风格要点」-「第一人称讲课体」一节。
- ❌ **口语填充词混同于口语气息**——原文的"um""you know""all right"等填充词要清理，但讲师的个人语气（反问、设问、课堂互动式的"对不对？""你们想想"）必须保留。清理填充词不等于磨平个性，详见「风格要点」。

## 工作流程

### 第 1 步：定位源文件和已有译文

标准路径结构：

```
源目录:   raw/courses/<course-id>/source/en/
译文目录: raw/courses/<course-id>/_prepared/translations/zh-CN/
```

任务：找到当前要翻译的源文件（`NN-topic.md`）和同一系列的最新一课译文。

**⚠️ 源文件截断陷阱**：`read_file` 默认只返回约 6000 字节（约 294 行）。如果源文件很大，会显示 `"truncated": true` 和 `"next_offset": N`。**必须在第一页读取后就检查结果中的 `file_size` 字段**，判断真实文件规模。如果 `file_size` 远大于已读内容，说明源文件跨度很大，需要多次 `read_file(offset=next_offset)` 直到 `truncated: false`。

实战案例（L18 特朗普世界秩序，2026-07-29）：源文件 2404 行 / 36,761 字符——但第一轮只读了前 294 行（6000 字节片），据此误判了真篇幅，第一版翻译仅 3267 字符。继续读取后续内容后才拿到完整论点（资源地缘博弈、杜金第三罗马、技术国方案、新旧秩序对抗、多重因素汇聚），第二版 5730 字符才达标。**永远不要因第一页就判断源文件篇幅**。

### 第 2 步：读取已有译文，提取风格特征

**读至少一课（首选最新一课，如 L8）。** 逐项检查：

| 特征 | 检查项 |
|---|---|
| frontmatter | `domain`, `tags`, `title`, `source`, `source_num`, `blocks`, `language`, `format` |
| 译者注 | `**译者注：**` 顶格一段落，说明本课定位+核心论题，可补充系列背景；后面接 `---` 分隔线 |
| 标题格式 | `# NN 中文标题 — 中文翻译` |
| 人称 | 讲师用"我/我们"；听众用"你们/各位/伙计们" |
| 口语标记 | "好了""对不对？""懂了吗？""信不信由你""猜怎么着？" |
| 修辞手法 | 设问、反问、排比、短句、重复 |
| 语气 | 亲切、直白、有感染力 |
| 加粗用法 | **强调词** 加粗 |
| 章节分隔 | `## 中文章节名` |
| 噪音处理 | 原文的 `>> [snorts]` 等标记在译文中全部删除 |
| 结尾风格 | 通常是收束性的口语收尾 |

### 第 3 步：统计 blocks 数

frontmatter 的 `blocks` 字段 = 原文段落数。用 awk：

```bash
awk 'NF {p=1} /^$/ {if(p) {count++; p=0}} END {print count+1}' <source_file>
```

### 第 4 步：翻译
**风格要点：**

- 短句为主，适合朗读
- 口语化但不啰嗦
- 关键数据用中文数字（"50 万美元"而非 "$500,000"）
- 英文术语首次出现时中文括号标注英文：如"胆小鬼博弈（game of chicken）"
- 有情绪转折和节奏变化
- 直接面向听众讲述，不是读书笔记

**第一人称讲课体（2026-07-29用户纠正）：**

这是本系列翻译最重要的风格规则。源文件是课堂讲课录音转写稿，译文也必须是课堂讲课。**译文不能看起来像一篇书评——不能有"讲者指出""讲者做了""讲者用了一个例子"这样的第三方叙述。** 讲师应该在译文中直接说话。

| ❌ 错误（第三人称书评） | ✅ 正确（第一人称讲课） |
|---|---|
| "讲者引入了一个核心概念叫升级阶梯" | "我先讲一个概念：升级阶梯" |
| "讲者用了一个两人打架的例子来说明" | "用两个人打架的例子来说明" |
| "讲者提出了核心论点：控制比主导重要" | "核心论点是：控制比主导重要——明白了吗？" |
| "讲者做了三个预测" | "我做出三个明确预测" |

具体操作要点：
- 消除所有的"讲者指出/讲者做了/讲者说/讲者用了一个"——直接让讲师说话
- 加入第一人称听课场景标记："你们想想""看明白了吗？""对不对？"
- 保留原文的课堂互动感——设问、反问、模拟学生提问
- 比喻和故事要有画面感（恶霸故事：写到"鼻青脸肿""安安静静吃自己的饭"而不是干巴巴的流程）
- 短段落、短句子、有节奏感
- 口语填充词（um, you know, all right）清理掉，但口语气息（反问、悬念、停顿）必须保留

**内容结构：**
- 保留原文的论述逻辑顺序——这是第一优先级
- 保留关键数据和核心论点
- **口语气息（"All right?"、"Guys?"、"Okay?" 等）不要一律删除**。判断标准：这个口语标记是否构成了主讲人的节奏感或个性？如果是保留的衡量语（"All right? So..." 可简化为"好了"、"好"），保留为好；如果是机械化的填充词（"um"、"like" 等），可以清理。目标是让译文「像主播在说话」，不是「像课本在念」
- 可以合并原文中过于重复的句式

**压缩决策优先级（从最重要到最可牺牲）：**
1. 主讲人的论证逻辑和递进感 — 绝对保留
2. 主讲人的个性和口吻 — 高度保留
3. 关键数据（百分比、年份、人名、事件） — 保留
4. 枝节案例/扩展讨论 — 可适度压缩
5. 原文重复的元话语 → 一言以蔽之 — 优先压缩

⚠️ **当用户反馈「感受不到作者口气」时，先检查第 2、3 项是否被压缩过度，而不是盲目在第 4、5 项上加料。**

⚠️ **「用词再准确一点」≠「更详细」。** 这是两个独立的维度。用户认可了压缩程度（第一版）后说"用词可以再准确一点"——意思是保持同样的篇幅和信息密度，但在术语选择、动词搭配、逻辑连接上更贴原文。不要理解成加内容。

### 质量门槛——硬性字数标准

**正文纯文本（排除 frontmatter）必须 ≥ 5000 个字符。** 2026-07-28 会话中用户先提出"怎么着也得保证4000个词以上"，随后在下一轮对话中纠正为"要求5000个字符以上，去把"，并最终确认"这是底线"。此后所有译文均以5000为硬性最低标准，不可妥协。

**详细度锁定规则**：当用户确认"这个标准可以的，之后就是这个标准"时，该课的正文字数即为后续课时的详细度锚点。此时目标字数从5000提升到该锚点数值。实战案例：L18（9195 chars）经2026-07-29确认为新标准，L19（9148 chars）对⻬该水平。

检查方法：
```bash
sed '1,/^# /d' <译文文件> | wc -m
```

- L9 (1148 blocks): ~4655 字符
- L10 (1372 blocks): ~6072 字符 — 密度和语气都经用户批准的标准版
- L11 (1551 blocks): ~5272 字符
- L12 (1570 blocks): ~8714 字符 — 2026-07-29 重译对标L18标准
- L13 (1141 blocks): ~7639 字符 — 2026-07-29 重译对标L18标准
- L14 (1225 blocks): ~6794 字符 — 2026-07-29 重译对标L18标准
- L15 (1208 blocks): ~7620 字符 — 2026-07-29 重译对标L18标准
- L16 (1616 blocks): ~8825 字符 — 2026-07-29 重译对标L18标准
- L17 (1534 blocks): ~9117 字符 — 2026-07-29 重译对标L18标准
- L18 (1197 blocks): ~9195 字符 — 2026-07-29 确认的详细度锚点（上限标准）
- L19 (1351 blocks): ~9148 字符 — 对标L18标准
- L11 (1551 blocks): ~8988 字符 — 2026-07-29 新译对标L18标准

⚠️ **blocks 权重**：源文件 blocks 数越大，译文应当越长

**⚠️ 下滑检测**：每做一课后，立即对比本课字数与上一课的字数。如果连续 2+ 课出现字数持续下降（警示序列：本轮会话中 L12/5050→L13/3150→L14/2500→L15/2200→L16/2100→L17/1600 第一版），说明你在不知不觉中压缩过头了。此时必须立即停下来，检查哪些关键内容被砍掉了，补回到与上一课同等密度水平，不可继续向下做新课。（注：修正后 L14-L16 均回到 5000+。）

**⚠️ 长期批次退化陷阱（2026-07-29用户纠正）**：当你在一次会话中连续处理 5+ 课时，会出现一个系统性退化模式——前 2-3 课能维持 9,000 字符标准，但从第 4 课起开始不自觉下滑（L15/7,620→L14/6,794→L13/7,639→L12/8,714）。用户会明确指出"我希望保持在9000个字符左右，为什么你越来越省略？"。这不是个别课时的内容差异造成的——这是注意力在长序列中疲劳导致的系统性偷工减料。

**防范措施**：
(1) 用 todo 系统为每一课建立 #chars 追踪看板，随时与锚点对比；
(2) 每完成一课用 `wc -m` 记录到 `references/lesson-character-counts.md`；
(3) 如果当前课字数低于上一课 15%+，暂停并补回到上一课水平再继续；
(4) 连续做 4 课后休息或切换任务类型重置注意力。
(5) 在写第一版前先用源文行数和blocks数估算合理篇幅——不要等到写出来才发现不足。

**修正方法**：被用户指出后，不要试图用一轮 write_file 解决。用 5-10 轮 patch 对压缩章节逐一补料，每轮增加 200-500 字符，逐步拉回到锚点水平。如果缺口超过 2,000 字符（如从 6,500→9,000），一轮增量式的逐节 patch（每节加 300-500 字，做 6-8 节）比 30 轮每轮加 80 字的微小补丁高效得多。逐节扩展时按三轴加料法进行。

**⚠️ write_file截断陷阱（2026-07-29确认）**：write_file返回的bytes_written按UTF-8字节数统计（中文3字节/字符），而`wc -m`按实际字符数统计。因此bytes_written=12,896≠wc -m=4,624字符。更大的风险：如果一次性写入超过~200行或约12KB，write_file可能因超时截断内容——文件被写入但内容不完整。

**防御措施**：
(1) 永远不要尝试用一次性write_file写出9,000字符的完整译文。
(2) 采用两遍打法：第一版用write_file写4,500-5,500字符的骨架（覆盖所有章节+译者注+标题分隔线），然后通过5-15轮patch扩展到目标字数（9,000左右）。
(3) L13-L19的实践中，所有达到7,000+字符的译文都经过了至少5轮patch扩展。如果一次性write_file后意外发现字符数远低于预期（如12,896 bytes→4,624 chars），不要惊慌或重试write_file——只需按增量扩展流程走patch管线即可。
(4) 每次patch后用wc -m验证字数，确保在往目标方向移动。

⚠️ 仔细对比本版与上一版字数——当你在一条多轮对话中持续工作时，很容易产生"已经写了很多了"的错觉而实际字数并未增长。wc -m的数字不会说谎。

⏳ 历史参考值见 `references/lesson-character-counts.md`。

### 节奏控制——逐课审批，不批量

**必须一课一确认，用户说"这篇可以了"/"这篇就可以了"才能做下一课。** 绝不能一口气做 5+ 课然后批量推送——不管用户之前是否说过"接着一个一个完成"，都要先让用户看过当前译文并批准。本会话中的重大教训：L12-L17 八节课一口气做完并推送，用户看到后因密度下降、字数缩水而全盘否决，导致每课都需要数轮对话重做。

正确流程：
1. 翻译一课
2. 展示给用户（可附上字数、行数信息，让用户了解密度水平）
3. 等待用户确认（"可以了"、"这篇就可以了"）
4. 只有确认后才 push + 做下一课

错误示范（来自本会话的教训）：
- ❌ 埋头连续翻译 L12–L17 八节课然后批量 push
- ❌ 用户说"接着一个一个完成"就自动连续做，没有停下来等确认
- ❌ 以为用户需要的是"进度快"，实际用户要的是"每一课都达标"
- ❌ 翻译 L12 时从 L11 的 5272 字符骤降到 3679 字符而不自查

### 用户确认模式

当你完成一课翻译后，用户可能会出现以下反馈模式：

| 用户说 | 意味着 | 你该做 |
|--------|--------|--------|
| "你是不是概括的有点多？我就是确定一下" | 我在了解你的策略，不是要你重做 | 回答策略，问是否需要改 |
| "之前的版本我是满意的" | 那个版本就是风格基准 | 以此版本为准继续后面的课 |
| "我认为用词可以再准确一点，概括的程度是可以的" | 篇幅和数据量OK，但选词要更贴 | 在保持同样篇幅下微调用词 |
| "这篇就可以了" / "这个可以了" | 这节课通过了 | 继续下一课 |
| "我的意思是之后的内容" | 继续按这个标准翻译后续课时 | 重复相同流程翻下一课 |
| "12-17会不会太概括了点" / "过分省略了" | 翻译密度低于参考锚点 | 对照上一课字数，检查是否丢失了关键论证节点或叙事骨架。补回内容到与 L10 同等密度水平 |
| "怎么着也得保证4000个词以上" | 字数不够 | 用 `wc -m` 检查正文字数。注意：这之后用户又提高标准到5000字符，见质量门槛一节 |

### 增量扩展技术（当用户授权"尽可能详细"时）

当用户给出"如果能详细，就尽可能的再详细一点"的绿灯信号时，或者密度锚点（如L18的9,195）已经锁定后，使用此系统化扩展流程：

#### 扩展流程

1. **绘制章节地图：** 将译文分解为10-12个独立章节（开场、各核心论点、案例、Q&A、结论等）。
2. **创建todo清单：** 每个章节作为一个todo item，全部`in_progress`，逐一处理。
3. **阅读对应源文：** 针对每个待扩展章节，重读源文对应部分，找出之前压缩的内容——具体的人名、百分比、年份、引语。
4. **定点注入：** 用`patch(mode="replace")`将该章节的简短版本替换为扩展版本。每次只改一个章节。
5. **增量验证：** 每扩展2-3个章节后运行`wc -m`确认增幅。实战节奏：L19通过9次patch从5,173→9,148字符。
6. **重复直到达标：** 直到字符数对⻬密度锚点为止。

#### 三轴加料法

扩展每个章节时从三个维度同时注入：
- **(a) 叙事完整度：** 补回之前压缩掉的论证逻辑和枝节案例
- **(b) 数据锚点：** 添加具体国名、百分比、年份、人名、美元金额
- **(c) 修辞节奏：** 完整翻译原文引语、增加递进转折句、恢复主讲人的语气节拍

#### 防重复陷阱

**⚠️ 长期批次退化陷阱（2026-07-29用户纠正）**：当你在一次会话中连续处理 5+ 课时，会出现一个系统性退化模式——前 2-3 课能维持 9,000 字符标准，但从第 4 课起开始不自觉下滑（L15/7,620→L14/6,794→L13/7,639→L12/8,714）。用户会明确指出"我希望保持在9000个字符左右，为什么你越来越省略？"。这不是个别课时的内容差异造成的——这是注意力在长序列中疲劳导致的系统性偷工减料。

**防范措施**：
(1) 用 todo 系统为每一课建立 #chars 追踪看板，随时与锚点对比；
(2) 每完成一课用 `wc -m` 记录到 `references/lesson-character-counts.md`；
(3) 如果当前课字数低于上一课 15%+，暂停并补回到上一课水平再继续；
(4) 连续做 4 课后休息或切换任务类型重置注意力。
(5) 在写第一版前先用源文行数和blocks数估算合理篇幅——不要等到写出来才发现不足。

**修正方法**：被用户指出后，不要试图用一轮 write_file 解决。用 5-10 轮 patch 对压缩章节逐一补料，每轮增加 200-500 字符，逐步拉回到锚点水平。如果缺口超过 2,000 字符（如从 6,500→9,000），一轮增量式的逐节 patch（每节加 300-500 字，做 6-8 节）比 30 轮每轮加 80 字的微小补丁高效得多。逐节扩展时按三轴加料法进行。

**⚠️ write_file截断陷阱（2026-07-29确认）**：write_file返回的bytes_written按UTF-8字节数统计（中文3字节/字符），而`wc -m`按实际字符数统计。因此bytes_written=12,896≠wc -m=4,624字符。更大的风险：如果一次性写入超过~200行或约12KB，write_file可能因超时截断内容——文件被写入但内容不完整。

**防御措施**：
(1) 永远不要尝试用一次性write_file写出9,000字符的完整译文。
(2) 采用两遍打法：第一版用write_file写4,500-5,500字符的骨架（覆盖所有章节+译者注+标题分隔线），然后通过5-15轮patch扩展到目标字数（9,000左右）。
(3) L13-L19的实践中，所有达到7,000+字符的译文都经过了至少5轮patch扩展。如果一次性write_file后意外发现字符数远低于预期（如12,896 bytes→4,624 chars），不要惊慌或重试write_file——只需按增量扩展流程走patch管线即可。
(4) 每次patch后用wc -m验证字数，确保在往目标方向移动。

⚠️ 仔细对比本版与上一版字数——当你在一条多轮对话中持续工作时，很容易产生"已经写了很多了"的错觉而实际字数并未增长。wc -m的数字不会说谎。

#### 反模式

- ❌ 一次性重写整个文件——字数可能并没怎么增加，只是重排了结构。
- ❌ 盲目在所有章节均匀加料——应定位真正被压缩的部分精准补料。
- ❌ patch失败后直接换write_file——用更多上下文重新定位old_string即可。

### 完全重译模式（当用户要求按新标准重做旧课时）

当用户说"你再把Lxx按这个标准重新翻译一下"时，使用此模式。这与增量扩展不同——不是在一份有缺陷的译文上补丁，而是从零开始按新标准重建。

#### 流程

1. 评估现有译文：读出当前译文，判断它的篇幅和结构。如果是极简版（小于5,000字符），不要试图在上面修补——直接重写。
2. 全量读取源文：源文件可能超过2,500行。分5-7段读取，每段300-400行，确保覆盖全部论点。读完后在头脑中建立完整的章节地图。
3. 第一次写入（骨架）：用write_file写一份约4,500-5,500字符的初版，覆盖所有主要章节，风格对齐最近批准的锚点版本。第一版的核心目标是结构完整——每个论点都在，节奏通顺。不要试图一次写到9,000字符——这会被write_file的200行/12KB限制截断。
4. 增量扩展至达标：第一版写完后用wc -m确认字数。然后调用增量扩展技术中的三轴加料法，通过5-10轮patch将字数从约5,000拉升到对齐密度锚点（9,000左右）。每2-3轮patch后检验一次字数。
5. 处理patch冲突：如果patch因Found 2+ matches失败，说明之前已往里加过类似内容。不要切换用write_file重写——用read_file确认当前文件状态，然后取更大上下文片段让old_string唯一化。

#### 实战案例（L17大重置，2026-07-29）

- 源文3,078行/47,700字节 — 用4次read_file各400行+1次290行读完
- 第一版：write_file -> 5,172字符（覆盖12个章节）
- 扩展轮：6次patch -> 银行机制 + 结构层 + 意识形态 + 2008危机 + BIS + 中国/以色列 + Q&A + 结语
- 最终：9,117字符 — 对⻬L18的9,195标准
- 耗时：约20次工具调用（读源文4次+写1次+验证1次+patch6次+验证6次+终验1次）

#### 批量处理优先级（当用户要求"全部重做"多个课时时）

当用户说"之前做过的，如果没有达到9000个字符的标准，全部重做"时，按以下步骤操作：

1. **检测并排序**：用 `wc -m` 检查所有相关课时的当前字符数，按缺口从大到小排序（缺口最大的优先处理）。
2. **逐课治理**：每次只做一个课时。从缺口最大的开始。完成一课后再到下一课。不要在课之间来回跳。
3. **进度追踪**：用 todo 系统记录每课的目标缺口和当前进度。每完成一课汇报进度（`L13: 6003→7639, need 1361 more`等）。
4. **注意疲劳效应**：当在一条长对话中连续重做 5+ 课时时，从第 4 课开始注意力疲劳会导致不自觉偷工减料。在每课开始前先确认该课的目标字数，写完后用 `wc -m` 验证。如果发现新的课时字数明显低于前一课，暂停并补充。
5. **一课一报告**：完成每课后用三行报告：当前字符数、覆盖章节数、与锚点差距。

#### 注意事项

- 重译旧课时，先读该课的**最新已批准确认版本**的风格作为锚点，而非读该课现有的失败版本
- 重译后，立即更新`references/lesson-character-counts.md`中的对应行
- 重译完成不等于批准——仍然需要用户确认"这篇可以了"才能继续
